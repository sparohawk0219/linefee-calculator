# Run C 섹터 정의

리뷰어는 자기 섹터 절만 읽고 수행한다. 먼저 `tools/prompts/C_COMMON.md`를 읽는다.
섹터는 "숫자가 만들어지는 경로"를 따라 나눴다: 시장 → 시뮬레이션·가격 → 자본 → 상대방 데이터 → 화면 → 결과 → 저장소.

| 섹터 | 맡은 질문 | 모델 | 주 대상 |
|---|---|---|---|
| C1 시장·커브 | 오늘 시장이 맞게 들어오는가 | sonnet | `linefee/market.py`, `curves.py`, 루트 `market_data.py`·`bbg.py` |
| C2 시뮬레이션·XVA 가격 | 노출과 비용 항목이 방법론대로인가 | opus | `linefee/engine.py`, `pricing.py`, `trade.py` |
| C3 규제자본·IM | 자본 숫자가 별표3대로인가 | opus | `linefee/regcap.py`, `reg/byeolpyo3.txt`, `simm.py` |
| C4 상대방 데이터 | 실데이터가 결정대로 마스터가 되었는가 | opus | `ui/store.py`, `local/scratch/build_master.py`, `data/counterparties.csv`, `local/data/` |
| C5 화면·권한 | 사용자가 넣은 것이 엔진에 그대로 가고, 권한이 지켜지는가 | sonnet | `app.py`, `ui/`, `tests/test_app.py` |
| C6 결과 합리성 | 끝단 숫자가 경제적으로 말이 되는가 | opus | 엔진 전체를 블랙박스로 |
| C7 저장소·문서 | 공개 저장소가 깨끗하고 문서가 현재 코드와 맞는가 | sonnet | git 추적 파일 전체, 이력, `docs/`, `README.md` |
| C8 방법론: 이론·업계 표준 | 방법론이 XVA 개념 체계와 업계 표준에 맞는가 | opus | `docs/METHODOLOGY_v1.md`, `DECISIONS.md`, 엔진 전체 |
| C9 방법론: 실무·회계 정합 | 라인피 숫자가 데스크 의사결정과 회계·리스크 숫자에 맞물리는가 | opus | 같음 + `app.py`의 결과 표시 |

C8·C9는 **확정 결정을 다시 볼 수 있는 유일한 섹터**다 (사용자 지시, 2026-11-26). 아래 "C8·C9 특칙"을 따른다.

## C1 시장·커브

1. **재가격**: KRW IRS(CD), SOFR, TONA, KRW CSA(CCS), JPY CSA 커브가 입력 상품을 Par로 돌려주는지. 허용오차와 실제 최대 오차.
2. **날짜**: 평가일, spot lag(상품·통화별), 영업일 달력 조합(서울·뉴욕·도쿄), 휴일에 걸린 결제일, 만기 롤. 한국 대체공휴일·임시공휴일 처리.
3. **FX**: spot과 선도 포인트, 100엔 표기 변환, 삼각 일관성(M20 범위는 제외하고 그 밖의 통화쌍), `_today_spot`의 spot→today 환산.
4. **스냅샷 처리**: 누락·만기 지난 항목, 영업일 아닌 as_of, `check_snapshot`이 놓치는 형식, 구 스냅샷(`load_legacy`)과의 차이.
5. **QuantLib 전역 상태**: 평가일 전역 설정이 두 시장(기준·legacy)이나 화면 재실행 사이에 새는지.
6. **블룸버그 받기 코드**(실행하지 말고 읽기만): 필드·티커 매핑, 실패 시 기존 스냅샷 보존, 부분 실패 처리.

## C2 시뮬레이션·XVA 가격

1. **모형**: 금리 OU(Hull-White) 경로 분산 = 모형 분산(M14, kappa 음수 포함), FX 로그정규, 상관행렬 보정(`_nearest_corr`)의 영향.
2. **재현성·오차**: 시드 고정, 대조 난수, 경로 수에 따른 표준오차, 같은 입력 두 번 실행 시 동일성.
3. **경로 가치**: t=0 경로 평균 = 오늘 가치, 선도 가치 일치(`trade_forward_value`), 지급 직후 노드, 원금 교환(CCS).
4. **비용 항목**: E/L(CVA), FVA(FBA 인정 여부), MVA, KVA(M1 `retained_net`, M5 r(t)), 첫날 이익, 순마진의 부호·할인·적분 가중치.
   `docs/METHODOLOGY_v1.md` 산식과 항목별 대조.
5. **헤지 구조**: CCP·BTB·딜러 라인(M8, M9: upfront는 BTB만, 헤지는 Par), `market_hedge`·`par_client`·`market_gap`.
6. **손익분기**: `breakeven` 수렴·미수렴 처리, `fee_unit_pv`, 수수료 위치(고정금리 가산·upfront)별 결과가 같은 값을 주는지.
7. **경계**: 0.25년·30년, 명목 0 근처, PD 0과 100%, 담보 통화 USD/KRW(`vm_ccy`).

## C3 규제자본·IM

모든 상수·산식은 `reg/byeolpyo3.txt` 조항 번호와 함께 확인한다.

1. **SA-CCR**: RC, PFE 승수, 만기요인 MF(M13), 감독 델타, 금리 듀레이션, 외환 add-on(M2: CCS는 FX만), 헤징셋, alpha 1.4, CCP(296).
2. **BA-CVA 축약형**: DS 0.65, 한계계수 0.5(M3), 유효만기 하한(M12), 업종 RW 표 `trade.BA_CVA_RW`, 투자등급 판정.
3. **신용 RW**: 고정 RW 경로와 기본내부등급법(M16: 120·123·124·126, 중소기업 조정, PD 100%), `credit_rw_profile` 만기 배열.
   외부등급 표(35~37)와 32조 공공기관 표는 C4가 데이터 쪽을 보고, 여기서는 엔진이 받은 RW를 맞게 쓰는지만.
4. **SIMM**: v2.8+2512(M15) 위험가중치·상관·통화 분류, 단독·임계치 없음(M7), `im_profile`, CCP IM.
5. **KVA 자본 경로**: CET1 13%(M4), 자본 경로가 시간에 따라 줄어드는 방식, 세후 요구수익률 변환.
6. **단위**: 원·외화, 연·일, 명목 대비 비율, 배열 모양.

## C4 상대방 데이터

결정 M16~M21, O6을 데이터 쪽에서 검증한다. 원본은 `local/data/counterparty_min.csv`, `dealers.csv`, `fi_ratings.csv`,
루트 `PD.xlsx`, `ISDA 체결 현황.xlsx`(없을 수 있음). 결과는 `data/counterparties.csv`(249행 내외).

1. **전수 대조**: `build_master.py`를 읽고 그 규칙을 **독립적으로 다시 구현**(스크립트를 import하지 말고 `local/scratch/C4/`에 새로 작성)해
   원본에서 마스터를 다시 만든 뒤 `data/counterparties.csv`와 행·열 단위로 비교한다. 다른 행은 전부 적는다.
2. **PD**: 열 선택(M19 감사 구분, M17a LDP, M21 공공기관), 옛 등급(M16b), BBB- 오타 정정, D 처리.
3. **신용 RW**: 딜러 20%(M17), 금융기관 외부등급(M16a: 증권사 35, 그 밖 37, 낮은 등급), 공공기관 32조(가·나·다), IRB 대상 판정과 매출 단위(억).
4. **CSA·담보 통화**: 딜러 VM+IM(M17), ISDA 현황의 적격담보와 `vm_ccy`, 기업 고객 무담보(M19 예외 목록).
5. **BA-CVA 업종·등급**: 업종명 → 업종 매핑(M18) 오분류(예: 키워드 오탐), 투자등급 판정(M19 BBB- 이상).
6. **읽기 쪽**: `ui/store.py`의 `check_row`·`counterparty()`가 열을 맞게 해석하는지, 이름 꼬리표 경고([등급 갱신 필요] 등)가 화면에 뜨는지.
7. **누락·중복**: 원본에 있는데 마스터에 없는 상대방, 같은 법인의 중복, 이름 충돌.

## C5 화면·권한

`streamlit.testing.v1.AppTest`로 실제로 돌린다 (`tools/golden_check.py`의 `ui_layer` 참고).

1. **권한**(O4, O5): 일반 사용자가 은행 파라미터·마스터·시장 기준 선택에 닿는 경로가 없는지. 관리자 인증 우회, secrets 없을 때 동작.
2. **입력 → 엔진**: 단위 변환(억/백만, %/bp, 100엔), 방향, 수수료 위치, 헤지 선택(IRS CCP/BTB/딜러 라인), 마스터 상대방 → `Counterparty`.
3. **상태**: `session_state` 콜백 순서, 입력이 바뀌었는데 이전 결과가 남는 경우(`input_signature`), 예시 거래 전환.
4. **검증·경고**: `validate`가 놓치는 조합, 마스터 꼬리표 경고, kappa 음수 경고(M14), 미수렴 표시.
5. **관리자 화면**: 마스터 편집 저장 시 추가 열(vm_ccy, rw_method, sales_eok) 보존, 파라미터 저장·복원.
6. **표시**: 결과 표·요약 문장이 엔진 값과 같은 숫자를 말하는지 (반올림 외 차이).

## C6 결과 합리성

엔진을 블랙박스로 두고 성질을 시험한다. 실패하면 원인까지 좁혀 해당 섹터 표시를 붙인다.

1. **항등식**: 비용 항목 합 = 총비용, 손익분기 수수료에서 순마진 = 0, 연도별 손익 합 = 총액.
2. **단조성**: 만기↑ → 노출·CVA·자본↑, PD↑ → CVA↑, 신용 RW↑ → KVA↑, CSA 없음 → VM → VM+IM에서 CVA↓·MVA↑.
3. **대칭·척도**: 명목 2배 → 비용 약 2배, 지급·수취 뒤집기의 부호, 통화 단위 바꿔 같은 거래.
4. **실거래 사례**(마스터의 실제 상대방 사용, 사례별 상대방과 이전 결과는 `local/controller/C_CASES.md`):
   - 은행 고객 ↔ 헤지 딜러 BTB 원화 IRS 5년 1,000억
   - 공공기관 30년 엔/원 CCS (golden의 jpykrw 조건)
   - 대기업 IRB 5년 CCS, 중소기업 IRB(매출 700억 이하)
   - 각 결과의 크기를 시장 관행(bp 단위 라인피)과 비교해 이상하면 적는다.
5. **PFE 대체 지표와 비교**: 루트 `여신환산율.xlsx`(없으면 생략)의 환산율과 SA-CCR add-on 비율을 같은 만기·상품에서 비교.
   M2·확정 결정과 다른 방법은 발견사항이 아니다. 크기 차이가 설명되지 않을 때만.
6. **안정성**: 경로 수 2배에서 결과 변화가 표준오차 안인지, 시드 바꿔도 손익분기 변동이 0.1bp 이내인지.

## C7 저장소·문서

1. **실데이터 유출**: git 추적 파일과 **전체 이력**(`git log -p --all`)에서 실제 상대방·딜러·고객 이름, 법인번호, 내부 등급, 한도.
   `data/counterparties.csv`·`local/data/`의 이름 목록과 대조해 찾는다. O10(이력 재작성 안 함)은 전제이므로,
   이력에만 있는 것은 P2로, 현재 추적 파일에 있는 것은 P1로 낸다.
2. **비밀값·내부 경로**: 토큰, 비밀번호, 이메일, 사내 경로, 사용자 개인정보.
3. **gitignore**: 실데이터·스냅샷·secrets·리뷰 노트가 모두 제외되는지, 새로 생긴 파일 유형이 빠졌는지.
4. **결정 구현 표**: DECISIONS의 M1~M21, O1~O11 각각이 코드·데이터·문서 어디에 구현되어 있는지 한 줄씩 찾는다.

5. **문서 ↔ 코드**: `METHODOLOGY_v1.md`(특히 7.3 신용 RW), `DESIGN.md`, `README.md`가 현재 코드와 맞는지. 실행 안내대로 새 clone이 돌아가는지.
6. **의존성**: `requirements.txt`와 실제 import, 버전 고정.

## C8·C9 특칙 (방법론 점검)

- `C_COMMON.md`의 "확정 결정은 전제" 규칙의 예외다. 확정 결정(M·O 항목)과 문서화된 방법론 자체를 평가한다.
  확정 결정에 대한 의견은 `category: "decision-conflict"`, 결정이 없는 영역의 개선안은 `category: "methodology"`로 낸다.
  모두 `touches_methodology: true`. 구현 대상이 아니며 사용자가 항목별로 본다.
- 결함 찾기가 아니다. **현행 방법이 무엇을 놓치고, 바꾸면 라인피가 어느 방향으로 얼마나 움직이는지**를 본다.
- 발견사항 한 건 = 개선 주제 하나. 필드 사용법:
  - `severity`: 우선순위. P1 라인피가 체계적으로 틀린 방향(과소·과대)으로 수 bp 이상 / P2 특정 상품·상대방에서 의미 있음 / P3 개념 정합성
  - `claim`: 현행 방법 한 줄 + 표준·이론과의 차이 한 줄
  - `expected_vs_actual`: 영향 추정 (방향, 크기, 어떤 거래에서). 가능하면 엔진으로 직접 근사 계산하고 방법을 적는다. 추정이면 추정이라고
  - `suggested_fix`: 개선안 + 필요한 데이터·작업량(소·중·대) + 권고(지금 개선 / 다음 버전 / 현행 유지 근거 있음)
  - `repro_command`: 영향 계산 명령이 있으면, 없으면 ""
- DECISIONS의 "근거" 열을 반드시 읽고, 그 근거가 왜 충분하지 않은지(또는 충분한지)를 적는다. 근거가 충분하면 내지 않는다.
- 이미 보류된 주제(포트폴리오·상계 집합 반영: 원장 연동 전까지 보류, `local/controller/STATE.md`)는
  "보류 중"으로 표시하고 영향 크기만 추정한다.
- 공개 문헌 검색(WebSearch)은 된다. 검색어에 실데이터(실명·등급·한도)나 은행 이름을 넣지 않는다.
- 최종 보고에는 점검표 대신 **주제별 판정표**(주제, 현행, 판정: 적합 / 개선 권고 / 의견 차이, 발견 id)를 낸다.

## C8 방법론: 이론·업계 표준

질문: "XVA 개념 체계(가격 조정 항목의 정의와 경계)로 보면 이 방법론은 완결적이고 일관적인가?"

1. **항목 구성**: CVA, DVA, FVA(FCA·FBA), MVA, KVA, ColVA(담보 이자율·담보 통화 선택권). 빠진 항목, 겹치는 항목(FBA와 DVA 이중 계산).
2. **확률 측도와 PD**: 내부 PD 마스터(실측 PD)를 쓴 CVA와 시장 내재(CDS·채권 스프레드) PD의 차이. 가격 조정이라는 성격에 맞는가.
3. **할인·담보**: CSA 담보 통화에 맞는 할인, 무담보 거래의 할인 커브, 조달 커브 선택(M5)과 FVA의 일관성.
4. **노출 정의**: EE·ENE, 담보 하 잔여 노출(MPOR, Threshold, MTA), 청산 가치 가정(무위험 vs 대체 비용).
5. **KVA**: 자본 범위(CCR, CVA 자본 외에 시장위험 자본·레버리지 비율), 요구수익률 방식(M1, M4), 자본 경로의 측도.
6. **모형**: 금리 1요인 Hull-White와 FX 로그정규, 변동성 보정, 장기(30년) 엔/원 CCS에서 베이시스·상관 가정의 충분성.
7. **확정 결정 재검토**: M1~M21 중 XVA 개념상 논쟁이 있는 것 (예: M10 wrong-way 제외, M11 등급 고정, M7 단독 IM, M3 한계계수).

## C9 방법론: 실무·회계 정합

질문: "이 라인피를 받으면 은행은 실제로 손해를 보지 않는가? 그리고 다른 부서 숫자와 맞물리는가?"

1. **의사결정 목적**: 이 숫자가 "고객에게 받아야 할 최소 라인피"를 말하는가. 손익분기 정의(순마진 0)가 그 목적에 맞는가.
2. **회계와의 정합**: IFRS 13 공정가치 조정(CVA·DVA·FVA 적립)과 라인피 산정 방식의 차이. 체결 첫날 회계상 적립액이 라인피보다 클 수 있는가.
3. **리스크·자본 부서 숫자와의 정합**: 은행이 실제 쓰는 PFE 대체 지표(루트 `여신환산율.xlsx`, 없으면 생략), 한도 사용액, 실제 자본 계산 방식(표준방법 vs 내부등급법)과의 차이.
4. **조달 비용(FTP)**: 은행 FTP 체계와 FVA·KVA 조달 스프레드(M5 alpha, 원화 담보 스프레드 임시 12bp)의 정합.
5. **헤지 실무**: BTB·딜러 라인·CCP 선택이 실제 데스크 관행과 맞는가, 헤지 비용(딜러가 우리에게 부과하는 XVA)을 반영하는가.
6. **파라미터 거버넌스**: 결과에 민감한 파라미터(LGD 60%, alpha, 요구수익률, 변동성 배율) 목록과 민감도. 누가 언제 바꾸는지.
7. **검증 가능성**: 사후 검증(실제 손실·자본 사용과 비교) 방법이 있는가, 동종 업계 라인피 수준과 비교할 수 있는가.
